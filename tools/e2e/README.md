# Isolated E2E harness for the DeepSeek Harness plugin suite

Reproducible, isolated end-to-end verification of this repo's DSH plugin suite
against the **installed** DeepSeek Harness **0.2.2-rc.1** desktop runtime, with a
deterministic mock LLM (no real API tokens) and no interference with the user's
live Harness app or `~/.dsh` home.

Everything lives under `tools/e2e/`. Every process the harness starts is spawned
by these scripts and killed by PID; the live desktop app, its profile and its
Web GUI are never signalled, reconfigured or reused.

```
tools/e2e/
├── bootstrap.sh                  # isolated DSH_HOME + custom profile + generated patches/scenario
├── start-web.sh                  # spawn mock LLM + isolated `dsh web`, wait readiness, login, record state
├── stop-web.sh                   # kill only the PIDs start-web.sh recorded
├── probe-web.mjs                 # login + read window.__DSH_BOOT__; assert client entries/bundles/host routes
├── run-session.mjs               # create a Session, prompt it, wait, dump + assert durable events
├── mock-llm.mjs                  # deterministic OpenAI-chat-completions SSE mock provider (no deps)
├── link-repo-root.sh             # register this checkout as a linked root (single @deepseek-ai/* copy)
├── probe-imports.sh              # risk probe: absolute-path plugin importing @deepseek-ai/* (baseline + workaround)
├── probe-tools.sh / .mjs         # model tool-path proof: scripted create_infini_goal call, tool row, goal
├── probe-install.sh / .mjs       # installed-profile proof: scripts/install-profile.mjs path, commands, driver
├── smoke.sh                      # self-test: boot, boot graph, host+client fixture plugin, text turn, tool-call turn
├── suite.sh                      # REAL SUITE E2E: build repo, dev-patch, boot, control plugin, scenarios
├── suite-drive.mjs               # pacing / quiet-window / pause scenario driver
├── lib/common.sh                 # shared shell helpers (paths, ports, readiness, safe process stop)
├── lib/web-client.mjs            # token login, boot-graph parse, /api Remote HTTP client, session helpers
├── artifacts/                    # committed screenshots from the Browser MCP UI proof (jpg)
├── config/...                    # generated by bootstrap.sh/suite.sh inside ${DSH_E2E_ROOT} (not in repo)
└── fixtures/
    ├── trivial-plugin/           # dual-face fixture inserted by ABSOLUTE PATH (host route + client DOM marker)
    ├── import-probe-plugin/      # imports @deepseek-ai/* and reports resolution/identity over HTTP
    └── e2e-control-plugin/       # suite run only: drives ctx.infiniGoals + ctx.agents over HTTP
```

`tools/e2e/lib/` holds the shared shell/Node helpers; it is tracked in the repo
(it used to be accidentally ignored by the root `lib/` gitignore rule).

## Prerequisites

| Requirement | Notes |
|---|---|
| DeepSeek Harness **0.2.2-rc.1** desktop app installed | harness uses the packaged launcher `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh` (override with `DSH_BIN`) |
| Node.js **>= 24.9** on `PATH` | matches the repo `engines.node` (esbuild `target: node24`, SDK scripts); override with `DSH_E2E_NODE` |
| `pnpm` + repo `node_modules` | `pnpm install` once; `suite.sh`/`probe-tools.sh` need `pnpm build` |
| free TCP ports **>= 34000** | `DSH_E2E_WEB_PORT` (34000) and `DSH_E2E_LLM_PORT` (34100) |
| no writes to `~/.dsh` | everything lives under `/tmp/dsh-e2e` (or `DSH_E2E_ROOT`) |

All scratch state goes to **`/tmp/dsh-e2e/`** by default:

| Path | Contents |
|---|---|
| `/tmp/dsh-e2e/home` | isolated `DSH_HOME` (profiles, sessions, credentials, storages) |
| `/tmp/dsh-e2e/config` | generated patch overlays, mock scenario, control-plugin patch |
| `/tmp/dsh-e2e/logs` | `web.log`, `mock-llm.log`, `mock-llm-requests.jsonl` |
| `/tmp/dsh-e2e/state` | `web.pid`, `llm.pid`, `web.url` (tokenized), `cookie`, `llm.port` |
| `/tmp/dsh-e2e/workspace` | Session working directory |
| `/tmp/dsh-e2e/documents` | isolated first-use Documents directory (default workspace) |
| `/tmp/dsh-e2e/smoke`, `/suite` | per-run artifacts/reports |

## Quick start

```sh
# 0. one-time: install repo dependencies (needed by plugin-bundle imports and by pnpm build)
cd /Users/guoyk/Workspace/src/dsh-infini-goal
pnpm install

# 1. harness self-test (fixture plugin by absolute path, deterministic mock LLM)
tools/e2e/smoke.sh
# -> SMOKE PASS (9 steps), stops everything at the end

# 2. real plugin-suite E2E (build + dev-patch + isolated boot + 3 scenarios)
tools/e2e/suite.sh --fresh
# -> SUITE PASS (9 steps)

# 3. import-resolution risk probe (absolute-path plugin importing @deepseek-ai/*)
tools/e2e/probe-imports.sh
# -> e2e probe: PASS

# 4. model tool-path proof (scripted create_infini_goal tool call)
tools/e2e/probe-tools.sh
# -> PROBE TOOLS PASS

# 5. installed-profile proof (scripts/install-profile.mjs, no --patch)
tools/e2e/probe-install.sh
# -> PROBE INSTALL PASS

# 6. keep an instance running for manual/browser checks
DSH_E2E_KEEP_RUNNING=1 tools/e2e/smoke.sh    # or suite.sh --only scenario1
# open the printed tokenized URL in a fresh browser tab
tools/e2e/stop-web.sh
```

The probes default to the same `/tmp/dsh-e2e` root and ports as the other
scripts; run them sequentially, or give each a separate root + port pair (see
"Running several instances at once" below).

Exact manual sequence, if you want to drive it step by step:

```sh
export DSH_BIN="/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh"
tools/e2e/bootstrap.sh --fresh                 # /tmp/dsh-e2e/home + profile `e2e` from the shipped `web` template
tools/e2e/start-web.sh                         # boot mock LLM :34100 + isolated `dsh web` :34000
cat /tmp/dsh-e2e/state/web.url                 # http://127.0.0.1:34000/?token=<launch token>
node tools/e2e/probe-web.mjs --print-entries   # boot graph (window.__DSH_BOOT__) report
node tools/e2e/run-session.mjs --prompt "hello e2e" --expect-assistant "MOCK_REPLY"
tools/e2e/stop-web.sh
```

Environment overrides (all optional):

| Variable | Default | Meaning |
|---|---|---|
| `DSH_BIN` | packaged launcher under `/Applications/DeepSeek Harness.app` | CLI to boot |
| `DSH_E2E_ROOT` | `/tmp/dsh-e2e` | scratch root (never `~/.dsh`) |
| `DSH_E2E_PROFILE` | `e2e` | custom profile name under `$DSH_HOME/profiles` |
| `DSH_E2E_WEB_PORT` | `34000` | Web port (must be `>= 34000`) |
| `DSH_E2E_LLM_PORT` | `34100` | mock LLM port (must be `>= 34000`) |
| `DSH_E2E_HOST` | `127.0.0.1` | bind address (concrete literal only) |
| `DSH_E2E_NODE` | `node` on `PATH` | Node used by harness scripts |
| `DSH_E2E_SCENARIO` | generated scenario | mock-LLM scenario JSON used by `start-web.sh` |
| `DSH_E2E_KEEP_RUNNING` | unset | `1` leaves the instance running after a check |

## What the harness proves

### `smoke.sh` (harness self-test, no repo suite involved)

1. **Isolation** — a fresh `/tmp/dsh-e2e/home`; the custom profile is created
   from the shipped `web` template with the boot-free `--dump-config` path:
   `DSH_HOME=... "$DSH_BIN" e2e --from-default-profile web --dump-config`.
2. **Readiness** — the instance prints exactly one readiness line once the
   Loader tree settles: `dsh web: http://127.0.0.1:34000/?token=<token>`.
3. **Host plugin by absolute path** — `fixtures/trivial-plugin/index.js` is
   inserted via `--patch` and registers `GET /e2e-trivial/health`; the config
   object from the patch row arrives intact.
4. **Client plugin by absolute path** — the fixture's hand-written
   `exports["./client"]` bundle registers through the lazy-CJS protocol
   (`window.__ModuleLoader__.load({ id, factory })`), appears in
   `window.__DSH_BOOT__.entries`, and executes in the page
   (`window.__E2E_TRIVIAL_CLIENT__ === true`, `#e2e-trivial-client-marker` in DOM).
5. **Scripted text turn** — create a Session over the Web API, prompt it, wait
   for idle; assistant text comes from the deterministic mock.
6. **Scripted tool call** — the mock next streams an OpenAI `tool_calls`
   completion; the `bash` tool really executes (`printf e2e-tool-ok`, requires
   the `description` argument), its result is fed back to the mock, and the
   final assistant answer is streaming text again.
7. **Deterministic mock accounting** — exactly 3 model requests, kinds
   `text,tool_call,text`, third carrying `hasToolResult: true`.
8. **Clean shutdown** — only harness PIDs are signalled; both ports are released.

### `suite.sh` (real plugin suite E2E)

1. `pnpm build` — builds the suite: 9 `lib/*.js` files across the plugin packages
   (the main `bundle` package is patch-only and emits no JS; `disable-goal-bundle`
   contributes its copied `preset-filter.js` runtime asset).
2. `node scripts/dev-patch.mjs` — writes `.tmp/cordis.patch.yml` inserting the
   five plugin rows by absolute path.
3. Isolated profile + **linked root** (`link-repo-root.sh`) so the bundles'
   `@deepseek-ai/*` imports resolve to the DSH installation's single copies
   (see "Import-resolution risk" below).
4. Boots the isolated Web instance with, in patch order:
   generated mock/isolation patches, the trivial fixture, `.tmp/cordis.patch.yml`,
   and `fixtures/e2e-control-plugin` (suite run only).
5. Asserts the composition: `ctx.infiniGoals` service mounted
   (`GET /e2e-infini/health` → `hasInfiniGoals:true`) and the browser boot graph
   contains `@yankeguo/dsh-client-ui-infini-goal` with a served client bundle.
6. Runs three scenarios (`suite-drive.mjs`) and observes the **durable Session
   log** over the same API the browser uses. PASS output includes timestamps.

## Discovered facts (DSH 0.2.2-rc.1)

### CLI / profile / patches

- Launcher: `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`
  (a shell wrapper that runs the Electron binary as Node against
  `app.asar/dsh/node_modules/@deepseek-ai/dsh-desktop-host/lib/cli.js`).
- Profile templates: `web`, `headless`, `acp`, `sdk`, `sdk-minimal`.
  A custom profile is created from one template, boot-free:
  `dsh <name> --from-default-profile web --dump-config`.
- Profile is `$DSH_HOME/profiles/<name>/{package.json,cordis.patch.yml,cordis.yml,pnpm-workspace.yaml}`;
  `package.json` → `dsh.profile.bundles = ["@deepseek-ai/dsh-base","@deepseek-ai/dsh-web-app"]`.
- `--patch <file>` is a launcher flag repeatable before the app args; overlays
  apply after the profile layer in argv order. Inserted plugin `name` values may
  be **absolute filesystem paths** (converted to file URLs by patch loading).
- App args start at the first token the launcher does not recognise:
  `dsh e2e --patch a.yml --no-open --port 34000 --host 127.0.0.1`.
- `dsh web --no-open` flags: `--host`, `--port`, `--public-url`,
  `--trusted-host`, `--tls-cert/--tls-key`. Wildcard binds are rejected.
- Boot is fast: ~0.5–1.5 s to the readiness line on this machine.

### Readiness, authentication, Web API

- Readiness line: `dsh web: <authenticated-url>`, i.e.
  `http://127.0.0.1:<port>/?token=<launch token>`; printed only after the
  Loader tree settles (safe readiness signal).
- Token exchange: `GET /?token=<token>` → **HTTP 303 See Other** with
  `Location: ./`, `Cache-Control: no-store`, and one `Set-Cookie`:
  `dsh-auth-<hash>=v1.<payload>.<sig>; Max-Age=2592000; Path=/; HttpOnly; SameSite=Strict`.
  The cookie is authority-bound (`127.0.0.1:34000` in payload).
- Without the cookie: `GET /` → **401**, `POST /api/...` → **401**.
  Static assets (`/plugins/...`) stay public and are served without auth.
- Boot graph injection: index HTML contains one global row
  `<script>globalThis["__DSH_BOOT__"] = {"rev":"...","entries":[...],"batches":[...]}</script>`
  (rows are `<`-escaped as `\u003c`).
- Remote unary calls go through the Connection HTTP bridge:
  `POST /api/<namespace>/<method>` with `Content-Type: application/json` and body
  ```json
  { "type": "client-request", "rpcId": "<id>", "method": "session/create",
    "payload": { "args": { "request": { "cwd": "/tmp/..." } } } }
  ```
  The Gateway envelope requires **exactly one** plain-object `args` field; each
  Remote parameter becomes a named `args` field. Session controller methods
  take one `request` parameter, so `payload.args.request = {...}`.
- Response: `{ "type":"server-response", "rpcId":"<same id>", "result": { "ok": true, "value": ... } }`
  or `{ "ok": false, "error": { "code", "message", "details" } }`.
  Streaming methods (`session/follow`, `session/observeState`, the `$events`
  pump) need the `/api/remote.mux` WebSocket; the harness deliberately uses only
  unary endpoints.
- Endpoints used (payload/response, verified):

  | Endpoint | Request `args` | Response value |
  |---|---|---|
  | `session/create` | `{request:{cwd?, workspaceId?, sessionId?, agentPreset?}}` | `{sessionId, agentPreset}` |
  | `session/prompt` | `{request:{requestId, sessionId, mode:"queue"\|"steer", content:[{type:"text",text}]}}` | `{accepted:true}` |
  | `session/state` | `{request:{sessionId}}` | `{cursor, active, running, queue, pendingInput}` |
  | `session/wait` | `{request:{sessionId, afterSeq?, timeoutMs?}}` | `{reason:"idle"\|"input-required"\|"timeout", state:{cursor,...}, output:{records}}` |
  | `session/events` | `{request:{address:{kind:"session",sessionId}, throughSeq?, maxMessages?}}` | `{cursor, records:[{type:"event",event:{type,seq,time,data}}], hasMore}` |

  `session/wait`'s `output.records` contain **assistant messages only**;
  `session/events` returns the full durable page (turn/step/tool/user events).
- `session/create` already logs 2–3 events (permission/sandbox/approval state);
  read `session/state.cursor` first, then `wait` with `afterSeq=cursor`.
- Observed session event types in a tool-calling turn:
  `permission/preset, sandbox/mode, approval/policy, agent/inbox/spliced,
  turn/start, step/start, system/message, user/message, request/header,
  request/context, session/title, session/title-llm-request,
  assistant/message, tool/call, tool/result, step/end, turn/end`.
  Event `time` is epoch milliseconds; `seq` is the durable ordering key.
- Client plugin contract: a package with `dsh.client: {platform:"web", inject?:[...],
  immediately?:bool}` and an `exports["./client"]` file. The browser bundle is the
  lazy-CJS registration form (`window.__ModuleLoader__.load({id: <package name>,
  factory: (require) => { ... return exports }})`). The host serves it under
  `/plugins/??<combo>`; the boot graph row id is the **package name** from the
  nearest `package.json` of the row's module location.
- A host plugin inserted by absolute path is found by walking up from the module
  file to the nearest `package.json`; that package name is what `/plugins` and
  the boot graph use.

### Mock LLM / provider configuration

- `@deepseek-ai/dsh-llm-pi-ai` with a hand-declared route speaks pi-ai's
  `openai-completions` protocol → `POST <baseURL>/chat/completions` with
  `stream: true`, `stream_options.include_usage: true`, SSE `data:` frames and a
  terminating `data: [DONE]`. A text completion is
  `delta:{role:"assistant"}` → N × `delta:{content}` → `finish_reason:"stop"` →
  a `choices:[]` chunk carrying `usage` → `[DONE]`. Tool calls stream
  `delta.tool_calls[{index,id,type:"function",function:{name,arguments}}]`
  fragments and finish with `finish_reason:"tool_calls"`.
- Profile patch that routes every model request at the mock (`mock-llm.patch.yml`):
  ```yaml
  - id: llm-pi-ai
    name: "@deepseek-ai/dsh-llm-pi-ai"
    config:
      providers:
        mock:
          api: openai-completions
          baseURL: http://127.0.0.1:34100/v1
          apiKeyEnv: MOCK_LLM_API_KEY
          models: [{ id: mock-model, name: Mock Model, contextWindow: 100000, maxTokens: 8192, input: [text] }]
  - id: agent-default-model
    name: "@deepseek-ai/dsh-agent-default-model"
    config: { provider: mock, model: mock-model }
  ```
  A keyless local OpenAI-compatible endpoint still needs a **placeholder
  credential**: export `MOCK_LLM_API_KEY=sk-e2e-placeholder` at launch (resolved
  through the credential seam: stored file → launch env → `.env`s).
- For determinism, the harness disables `session-title-first-prompt-llm`
  (`- id: session-title-llm / disabled: true`): it is an auxiliary model call
  that would consume one scripted mock step. The fallback title path still logs
  `session/title`.
- `DSH_PERMISSION_MODE=danger-full-access` is exported at launch so approval
  policy is `never` and scripted tool calls run non-interactively. (Permission
  presets are otherwise `workspace-write` + `ask`, which would block a headless
  harness.)
- The `bash` tool requires a `description` argument in its JSON arguments;
  omitting it produces a `ToolArgsError` tool result (`isError:true`).

### Isolation details

- The instance's first-use default Workspace is
  `<Documents>/deepseek-harness/default-workspace`. The generated
  `isolation.patch.yml` overrides the workspace controller:
  ```yaml
  - id: workspace-controller
    name: "@deepseek-ai/dsh-api-workspace-controller"
    config: { documentsDirectory: /tmp/dsh-e2e/documents }
  ```
  so a UI-created Session lands under `/tmp/dsh-e2e/documents/...`, not in the
  user's real `~/Documents` (verified: the user's directory mtime is unchanged).
- Session logs are stored under `$DSH_HOME/sessions/<escaped-workspace>/session-<uuid>/session.v4.jsonl.zstd`;
  the harness reads them through the API instead of parsing the compressed log.
- `bootstrap.sh --fresh` refuses to delete anything whose path does not start
  with `/tmp/`.

### Import-resolution risk (important for the real suite)

A plugin inserted **by absolute path** whose host half imports `@deepseek-ai/*`
resolves those imports **natively** (through the importer's real ancestor
chain) unless the importer is inside an *interception layer*:

- **Baseline** (no setup): `import.meta.resolve('@deepseek-ai/cordis')` returns
  the repo's own pnpm copy:
  `/Users/.../dsh-infini-goal/node_modules/.pnpm/@deepseek-ai+cordis@4.1.0.../lib/index.js`.
  The plugin mounts and works, but the process then holds a **second copy** of
  cordis/dsh-llm/dsh-session: `ctx instanceof Context === false`. This is the
  fragile identity split real plugins must not live with.
- **Workaround (required, automated by `link-repo-root.sh`)**: symlink the repo
  checkout under the active profile's `node_modules`:
  ```sh
  mkdir -p /tmp/dsh-e2e/home/profiles/e2e/node_modules
  ln -sfn /Users/guoyk/Workspace/src/dsh-infini-goal \
           /tmp/dsh-e2e/home/profiles/e2e/node_modules/e2e-repo-root
  ```
  DSH then treats that directory as a **linked root**: importers below it use
  peer-aware ancestor lookup, and at each `node_modules` position the current
  package's `peerDependencies` names present in the installation's runtime
  table resolve to the **installation package**. Result (verified):
  `@deepseek-ai/cordis` → `file:///Applications/DeepSeek%20Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/cordis/lib/index.js`,
  `ctx instanceof Context === true`, `Service` subclass imported from the
  runtime copy mounts and is retrievable. Insertion by absolute path keeps
  working; no package-name install/symlink-per-package is needed.
- `probe-imports.sh` runs both modes and requires the workaround to be green:
  ```
  baseline : repoCopy=true  installationCopy=false contextIdentity=false checks={createUserMessage:true,sessionIdBrand:true,serviceMount:true,serviceSameCordis:true}
  workaround: repoCopy=false installationCopy=true  contextIdentity=true  checks={all true}
  e2e probe: PASS
  ```
  Raw reports: `/tmp/dsh-e2e/smoke/import-probe-{baseline,workaround}.json`.

## Mock LLM scenario format

`mock-llm.mjs` consumes one scripted step per `/v1/chat/completions` request, in
order; when the script is exhausted it answers with a deterministic echo
(`MOCK_REPLY: <last user text>` or `FINAL: mock LLM saw the tool result (...)`),
so a Session always terminates. Auxiliary calls (e.g. the title LLM) shift the
sequence — the harness disables that one; if a future composition adds others,
add their steps to the scenario or disable them.

```json
{ "responses": [
  { "kind": "text", "text": "MOCK E2E first turn",
    "chunks": ["MOCK E2E ", "first ", "turn"] },
  { "kind": "tool_call", "tool": "bash",
    "arguments": { "command": "printf e2e-tool-ok",
                   "description": "echo the deterministic E2E marker" } },
  { "kind": "error", "status": 429, "message": "rate limited" },
  { "kind": "hang" }
] }
```

Step kinds: `text` (optional explicit `chunks`), `tool_call` (one call, arguments
split across two deltas), `error` (HTTP provider failure), `hang` (never
answers — for cancellation paths).

Mock server surface (all on `127.0.0.1:<llm port>`):

| Route | Purpose |
|---|---|
| `POST /v1/chat/completions` | OpenAI-compatible streaming completion |
| `GET /v1/models` | OpenAI-shaped model list |
| `GET /health` | `{ok, requests, remaining}` |
| `GET /__mock/requests` | `{"requests": [...]}` log array (also appended to `logs/mock-llm-requests.jsonl`; `fetchMockRequests` also accepts a bare array) |
| `GET /__mock/scenario` | scenario + cursor |
| `POST /__mock/reset` | reset cursor + request log |

Each logged request records `stepKind`, `lastRole`, `hasToolResult`,
`lastUserText`, `userTexts[]`, `toolNames[]`, `messageCount`, `cursor`.

## Real-suite E2E: control plugin and scenarios

`fixtures/e2e-control-plugin/index.js` is inserted only in the suite run. It is
dependency-free at runtime and **injects on the suite services**, so it activates
only when they are present:

```js
export const inject = ['agents', 'infiniGoals']
```

It registers a prefix route on the isolated Web server (plain named route, not
the authenticated `/api` bridge — it exists only in the isolated loopback
instance):

| Route | Behavior |
|---|---|
| `GET /e2e-infini/health` | `{ok, hasInfiniGoals, agents:[{id}], roots:[{id}]}` |
| `POST /e2e-infini/create` `{sessionId?, objective, minIntervalMs?, quietWindows?, timezone?}` | resolve live Agent via `ctx.agents.get(id)` (or first root) → `ctx.infiniGoals.create(agent, request)` → `{agentId, view}` |
| `GET /e2e-infini/status?sessionId=` | `ctx.infiniGoals.get(agent)` + `ctx.infiniGoals.plan(agent)` + `now` |
| `POST /e2e-infini/pause` / `resume` `{sessionId?}` | view → CAS `{id,revision}` → `ctx.infiniGoals.pause/resume` |

Round observation uses the **existing** Web API (`POST /api/session/events`):
round-start messages are `user/message` events whose `event.data.source.kind`
is `infini-goal` (`{kind, goalId, revision, round}`), with epoch-ms `event.time`.

`suite-drive.mjs` scenarios (each creates a fresh Session first):

1. **Pacing** — create an active goal with `minIntervalMs: 2000`; wait for
   rounds 1,2,3; assert each round number appears, that consecutive round-start
   event times differ by `>= 2000 − 50` ms, and `view.roundsStarted >= 3`.
2. **Quiet window** — create a goal whose quiet window covers "now"
   (`start = now−2 min`, `end = next local minute` in the goal timezone, with
   ≥ 8 s of window remaining); assert `plan.reason === 'quiet-window'` and
   `plan.quietUntil` set, no rounds advance during 3 s, then wait for
   `quietUntil === null` and assert the next round starts within 10 s.
3. **Paused** — create a goal, wait for the first automatic round (proves the
   driver works), `pause`, then assert `phase === 'paused'` and the round count
   does not change for 5 s.

Verified run (`suite.sh --fresh`, frozen tree, 2026-11-05, isolated
`/tmp/dsh-e2e-final`, mock model, live plugin suite):

```
PASS scenario1 automatic rounds respect minIntervalMs
  roundStarts: [{"round":1,...,"seq":9},{"round":2,...,"seq":22},{"round":3,...,"seq":31}]
  gapsMs: [2021,2011]
  roundsStarted: 3
  plan: {"reason":"interval",...}
PASS scenario2 quiet window suppresses then releases rounds
  window: {"start":"16:44","end":"16:48","timeZone":"Asia/Shanghai",...}
  roundsDuringWindow: 0
  firstRoundAfterQuiet: ...   delayAfterQuietMs: 27
PASS scenario3 paused goal produces no automatic rounds
  roundsBeforeWait: 1  roundsAfterWait: 1  view: {"phase":"paused","roundsStarted":1}
```

## Script reference

### `bootstrap.sh [--fresh]`

Creates `${DSH_E2E_ROOT}/{home,workspace,state,logs,config}`, the custom profile
from the shipped `web` template, and generates:

- `config/mock-llm.patch.yml` — mock provider route + default model + title-LLM off
- `config/isolation.patch.yml` — first-use workspace under `/tmp`
- `config/trivial-plugin.patch.yml` — fixture plugin inserted by absolute path
- `config/scenario.json` — default text/tool-call scenario

`--fresh` deletes `${DSH_E2E_ROOT}` first (refused for non-`/tmp` roots).

### `start-web.sh [extra-patch.yml ...]`

Validates overlays and ports, then spawns (only its own PIDs):
1. `mock-llm.mjs` on `DSH_E2E_LLM_PORT`, waits `/health`;
2. the isolated CLI boot:
   `DSH_HOME=… DSH_PERMISSION_MODE=danger-full-access MOCK_LLM_API_KEY=sk-e2e-placeholder dsh e2e --patch … --no-open --host 127.0.0.1 --port …`;
3. waits for the readiness line, saves `web.url`, exchanges the token for the
   cookie (`state/cookie`), and probes `/e2e-trivial/health`.
Extra positional patches are appended after the generated ones (last row wins),
which is the hook for the suite/dev overlay.
On failure, everything this script spawned is stopped automatically.

### `stop-web.sh`

SIGTERM (`then SIGKILL` after 15 s) only the PIDs in `state/{web,llm}.pid`,
removes ephemeral state. Logs and the isolated home are kept for inspection.

### `probe-web.mjs --state-dir <dir> [--assert-client-entry <pkg>] [--assert-client-bundle <pkg>] [--assert-host-route <path>] [--print-entries] [--json]`

Logs in, reads the served index, parses `window.__DSH_BOOT__`, then asserts:
entry presence, served bundle (`HTTP 200` + `__ModuleLoader__.load` + package
name), and host route `GET` 200. Exit 1 on any failure.

### `run-session.mjs --prompt <text> [--prompt …] [--session-id <id>] [--cwd <dir>] [--expect <substr>] [--expect-assistant <substr>] [--events-out <file>] [--json]`

Creates (or reuses) a Session through the Web API, prompts sequentially, waits
for each turn to go idle, then reads the full durable event page. Reports
`eventTypes`, `assistantTexts`, `toolCalls`, `toolResults`, mock request count,
and assertions. `--json` for machines, `--events-out` writes raw records.

### `mock-llm.mjs --port <n> [--host] [--log <jsonl>] [--scenario <json>] [--model]`

See "Mock LLM scenario format".

### `probe-imports.sh`

Baseline vs linked-root import-resolution probe; PASS requires the workaround.
Requires the repo's `node_modules` (`pnpm install`).

### `link-repo-root.sh`

Idempotently creates `${DSH_HOME}/profiles/<profile>/node_modules/<name>` →
repo root (`DSH_E2E_REPO_LINK_NAME`, `DSH_E2E_REPO_LINK_TARGET`). Must run after
`bootstrap.sh` and before `start-web.sh`.

### `probe-tools.sh` / `probe-tools.mjs`

Model tool-path proof (section 3): boots the suite composition with a mock
scenario that streams `create_infini_goal`, asserts the advertised tool list,
the successful tool result carrying the created goal, and the scripted final
answer. Requires a built suite and `.tmp/cordis.patch.yml` (run `suite.sh` once
or `pnpm build && node scripts/dev-patch.mjs`).

### `probe-install.sh` / `probe-install.mjs`

Installed-profile proof (section 4): fresh isolated home, then the real
`scripts/install-profile.mjs` path, then boots without the dev patch and asserts
no load errors, the boot-graph client row, `commands/list`/`commands/execute`
for `/infini-goal`, an automatic driver round, the three advertised model tools,
and the shared goal view through the control plugin.

### `smoke.sh` / `suite.sh`

One-shot self-tests described above. Both stop everything at the end unless
`DSH_E2E_KEEP_RUNNING=1`; both print PASS/FAIL step summaries and keep
per-run artifacts under `/tmp/dsh-e2e/{smoke,suite}`.

### Running several instances at once

Every script derives all paths from `DSH_E2E_ROOT` and all ports from
`DSH_E2E_WEB_PORT`/`DSH_E2E_LLM_PORT`, so independent runs can coexist (this is
how the proof runs above were captured while another agent used 34300/34301):

```sh
DSH_E2E_ROOT=/tmp/dsh-e2e-a DSH_E2E_WEB_PORT=34600 DSH_E2E_LLM_PORT=34601 ... 
DSH_E2E_ROOT=/tmp/dsh-e2e-b DSH_E2E_WEB_PORT=34700 DSH_E2E_LLM_PORT=34701 ...
```

`start-web.sh` refuses to attach to a foreign listener, so a wrong port can
never disturb another instance.

## Troubleshooting & limitations

- **Ports in use** — `start-web.sh` refuses to attach to a foreign listener on a
  harness port. Change `DSH_E2E_WEB_PORT` / `DSH_E2E_LLM_PORT` (both ≥ 34000).
- **`node` not found** — set `DSH_E2E_NODE`; scripts require Node ≥ 20.
- **Suite import identity split** — if `probe-imports.sh` baseline passes but
  `workaround` reports `contextIdentity:false`, the linked-root symlink is
  missing (run `link-repo-root.sh`) or `DSH_E2E_PROFILE` changed after linking.
- **Scripted tool calls blocked** — the harness exports
  `DSH_PERMISSION_MODE=danger-full-access`. If you launch the CLI yourself,
  keep that env or use a read-only prompt that needs no tools.
- **Extra model calls shift the mock sequence** — disable auxiliary LLM rows
  (see `session-title-llm`) or extend the scenario.
- **Streaming observation** — the harness uses unary endpoints only; live token
  deltas require the `/api/remote.mux` WebSocket and are intentionally out of
  scope (`run-session` observes committed turns/events).
- **Browser MCP check is manual** — the tool is agent-driven, not callable from
  a shell script; `probe-web.mjs`, `probe-tools.sh` and `probe-install.sh` are
  the automated equivalents for authentication + boot graph + bundle serving +
  host routes + command/tool/driver paths.
- **Shared Chrome via Browser MCP** — several agents may drive the same browser.
  Always `tab select <your tab>` immediately before each read/action batch, and
  `screenshot` right after selecting: the capture follows the attached tab, and
  another agent's tab can otherwise appear in the image. Close your tab and
  re-select the tab that was active before you started.
- **Screenshot artifacts** — the Browser MCP returns a normalized copy under
  `~/.dsh/attachments/...` (read-only); copy it into `tools/e2e/artifacts/` and
  `chmod 644` (files copied from that store are mode 400).
- **Concurrent instances** — use a distinct `DSH_E2E_ROOT`/port pair per
  instance; ports below 34000 are rejected and occupied ports are refused, never
  hijacked. Stale state is safe to remove with `bootstrap.sh --fresh` (guarded
  to `/tmp/*`).
- **Sandbox** — this session runs with danger-full-access; if the harness is
  later run under a narrower sandbox, writes outside the workspace (including
  `/tmp/dsh-e2e`) will be denied.
- The user's live Desktop app / `~/.dsh` are never touched: every `dsh` process
  is launched with its own `DSH_HOME`, its own profile name, its own ports, and
  its own working directory (empty scratch workspace, so no project `.env` is
  picked up).
