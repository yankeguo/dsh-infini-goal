# v0.3.0-rc.1 — DevLead relay 授权与 quiet-window 24:00 边界修复

本版本是一个 **release candidate**，汇总 v0.2.3 以来的两类 minor 变更：受控的 DevLead
relay 授权，以及 quiet-window 的 `24:00` 当日结束哨兵。8 个发布包统一升到
`0.3.0-rc.1`。DSH 兼容范围、持久化记录格式与已有目标数据均不变，升级无需手工迁移。

> **发布状态**：本版本以 `next` 暂存，暂存阶段不会公开任何版本。维护者 approve 之前，
> npm `latest` 仍是 `0.2.3`；approve 之后 `next` 指向 `0.3.0-rc.1`，`latest` 不会因此移动。

## 变化

### DevLead relay 授权（delegated human）

- `create_infini_goal` / `update_infini_goal` 现在接受一种受控的委托人类授权：在 runtime
  root agent 的当前 open turn 内，`user/message` 的 source 为
  `{ kind: 'devlead', form: 'relay', senderSessionId: <非空字符串> }`。
- 该形状是与独立安装的 DevLead 插件之间的**软协议契约**：本地字面量 + 结构校验，
  不 import、不依赖 `@yankeguo/dsh-devlead*`。额外字段忽略，以保持前向兼容。
- relay 与 direct human 等价，覆盖 create / edit / config / resume / pause / complete /
  blocked；blocked 不受 automatic-round 的 `blockedAfterConsecutiveRounds` 阈值限制，
  也不注入自动轮次的收尾提示。
- relay 仍必须落在 runtime root 与当前 open turn：落到 subagent、历史 turn，或形状为
  `notice` / 缺字段 / 空 `senderSessionId` / 未知形状时一律 fail closed。定时任务、
  subagent、agent-team、其他 agent 消息与 runtime notice 仍不授权。
- 相关文档与不变量已同步（AGENTS.md、README、DESIGN、bundle README、COMPATIBILITY）。

### quiet-window 的 `24:00` 当日结束哨兵

- 窗口的 `end` 现在可以写 `24:00`，表示开始日的结束（次日本地 00:00）；`start` 仍限制在
  `00:00-23:59`，`start == end` 仍因 zero-length 被拒绝。
- 修复了旧的 `Fr 18:00-23:59; Sa 00:00-23:59` 配置在周五 23:59:00–23:59:59.999 留出
  一分钟可触发空洞的问题。历史 `end=23:59` 会在文本、对象与持久化回放三条路径统一
  归一化为 `24:00`，已有配置与 Session 日志可直接生效。
- `00:00-24:00` 是显式全天形式；解析器接受，但若窗口并集覆盖全部本地时间，调度器仍以
  `RangeError` / `INFINI_GOAL_INVALID_SETTINGS` 拒绝。
- `formatQuietWindows` 输出规范 `24:00`；跨午夜、DST（含 America/New_York 回拨日与
  America/Santiago 午夜 gap）和跨年边界均有测试覆盖。

### projection checkpoint `stateVersion` 3

- quiet-window 归一化改变了 fold 结果：旧 v2 checkpoint 中可能仍保存 `end:'23:59'`，
  直接做 pause/resume/complete/blocked 的 suffix replay 会与 full replay 不一致。
- `infiniGoal` projection 的 `stateVersion` 从 2 升到 3：旧 checkpoint 行被丢弃，durable
  Session log 重新 fold 并归一化；`foldStateFromProjection` 另对同版本 checkpoint 做
  防御性 quiet-window 归一化。

## 安装 / 升级

rc 版本必须显式指定精确版本（`latest` 仍指向 `0.2.3`，不会自动升级到 rc）：

```sh
# 推荐：安装 bundle（会带入整套同版本包）
dsh plugin --profile desktop add @yankeguo/dsh-infini-goal-bundle@0.3.0-rc.1

# 或直接安装单个包（需要自行保证同版本）
dsh plugin --profile desktop add @yankeguo/dsh-tool-infini-goal@0.3.0-rc.1

# 本地 checkout
pnpm install && pnpm build && pnpm install:profile
```

更新后需要重启 DSH（host 插件与 preset 行在启动时绑定），并刷新 Web 页面；已有目标数据
无需迁移。

## 发布与审批

推 `v0.3.0-rc.1` tag 后，[`.github/workflows/publish.yml`](../../.github/workflows/publish.yml)
通过 OIDC 将 8 个包以 dist-tag `next` 暂存到 npm 私有暂存区。**暂存阶段没有任何版本公开**，
CI 不创建 GitHub Release，也不修改 `latest`。

维护者审查并由本机 2FA approve 后，版本才会公开，脚本同时创建标记为 prerelease 的
GitHub Release：

```sh
node scripts/promote-release.mjs --version 0.3.0-rc.1 --list-only   # 审查暂存结果
node scripts/promote-release.mjs --version 0.3.0-rc.1               # approve（2FA）+ GitHub Release
```

approve 前 `latest` 保持 `0.2.3`；approve 后 `next` 指向 `0.3.0-rc.1`，`latest` 仍保持
`0.2.3`。rc 不是 stable，本版本不会移动 `latest`。

## 已知限制 / 非阻塞后续项

以下为 quiet-window 复核留下的 low-severity 项，不影响本 rc 的授权、调度或升级路径：

- v3 checkpoint 若只做 restore、没有任何后续 owned event，projection 值可能暂时保留旧的
  `end:'23:59'` 文本；调度数学仍把它解释为 `24:00`，下一次 owned event 会归一化。
- v2 checkpoint 的四种生命周期迁移在 projection 层均已覆盖，service 层补齐了 pause 的
  suffix replay；resume/complete/blocked 的 service 级 restore 矩阵可在后续版本补充。
- 混合 registration restore（`infiniGoal` v3 与其他 projection unit 的旧 checkpoint 行
  同时存在）未单独做集成测试；DSH 按 unit 独立做 version gate。
